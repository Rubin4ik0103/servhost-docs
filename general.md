# Общая информация

## Перед началом

- Убедитесь, что доступна VNC или веб-консоль, и проверьте вход в неё.
- Сохраните резервную копию конфигурации сети для своей ОС.
- Запишите текущие адреса и маршруты: Linux `ip a`, `ip route`; FreeBSD `ifconfig -a`, `netstat -rn -f inet`; Windows `Get-NetIPAddress`, `Get-NetRoute`.
- Не удаляйте основной IP. Выполняйте действия по одному.
- Настройка внутри ОС выполняется клиентом самостоятельно. Держите текущую SSH/RDP-сессию открытой и проверяйте новую сессию отдельно.

> Настройка сети может прервать удалённый доступ. Если нет работающей консоли, сначала обеспечьте её доступность.

## Четыре разных состояния

1. **IP назначен услуге**: адрес отображается в панели. Это не подтверждает настройку внутри системы.
2. **IP добавлен в ОС**: виден в `ip -br a`, `ifconfig` или `Get-NetIPAddress` на существующем интерфейсе.
3. **IP принимает входящие соединения**: маршрут, firewall и конкретный сервис разрешают подключение к адресу.
4. **IP используется как исходящий**: внешний сервис видит его в исходящем соединении. Само добавление IP этого не гарантирует; могут понадобиться выбор source IP и отдельная маршрутизация.

Обычно дополнительный IPv4 добавляется к существующему сетевому интерфейсу, без отдельной физической карты. Основной IP и текущий default gateway сохраняются. Не добавляйте второй default gateway без явно предоставленной схемы маршрутизации.

## Подставьте свои значения

| Обозначение | Откуда взять |
| --- | --- |
| `<MAIN_IP>`, `<ADDITIONAL_IP>` | Основной и купленный IP в панели услуги, сверьте с ОС |
| `<INTERFACE>` | Linux: `ip -br a`; FreeBSD: `ifconfig -a`; Windows: `Get-NetAdapter` |
| `<GATEWAY>` | Действующий `ip route`, `netstat -rn -f inet` или `Get-NetRoute`; для дополнительного IP обычно не нужен новый |
| `<PREFIX>` | Параметры дополнительного адреса у провайдера; не копируйте префикс основного IP автоматически |
| `<NETMASK>` | Маска FreeBSD, соответствующая выданному префиксу дополнительного IP |
| `<ACTUAL_FILE>`, `<USER>`, `<CLIENT_IP>` | Фактический сетевой файл, имя пользователя для SSH и адрес устройства, с которого проверяете соединение |
| `<PROFILE>`, `<PROFILE_UUID>` | Имя и UUID активного соединения AlmaLinux из вывода `nmcli` |
| `<DNS_1>`, `<DNS_2>` | Действующие DNS либо выданные параметры, менять для второго IP обычно не требуется |

> Если префикс или способ маршрутизации дополнительного адреса не указан в параметрах услуги, уточните его в поддержке до изменения конфигурации. Нельзя безопасно угадать маску по адресу основного IP.

## Настройка в Linux

Для инструкций Linux с `networking` проверьте активную службу и найдите блок нужного интерфейса:

```bash
ip -br a
ip route
systemctl is-active networking
sudo cat /etc/network/interfaces
sudo ls -l /etc/network/interfaces.d
```

Файл с блоком `iface <INTERFACE> inet ...` может быть `/etc/network/interfaces` или подключённый файл в `interfaces.d`. Не меняйте сеть, если нужный блок или активная служба не найдены. Следуйте [инструкции по networking](linux/interfaces.md). Для AlmaLinux сначала проверьте NetworkManager по [отдельной инструкции](linux/almalinux-8-9.md). Для FreeBSD используйте отдельную страницу [FreeBSD 13](freebsd/freebsd-13.md) или [FreeBSD 14](freebsd/freebsd-14.md); Windows настраивается через свойства адаптера.

## Проверка после применения Linux

```bash
ip -br a
ip route
ping -c 3 <GATEWAY>
curl -4 https://api.ipify.org
```

Проверяйте `ping <ADDITIONAL_IP>` и SSH к нему **с другой машины**, а не только с этого VPS. ICMP может быть закрыт, поэтому отсутствие ping само по себе не доказывает недоступность IP. `curl -4` без выбора source показывает текущий исходящий адрес, который может остаться основным. Для проверки исходящего соединения с выбранным source IP можно выполнить `curl -4 --interface <ADDITIONAL_IP> https://api.ipify.org`; неуспех требует отдельной проверки маршрута и не означает, что входящие подключения не работают. Подробнее: [диагностика](troubleshooting.md).
